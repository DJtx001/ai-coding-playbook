一句话心智模型：新手想的是"怎么让 AI 写出我要的代码"，高手想的是"怎么让 AI 的产出可以被验证"。
下面八步，每一条都是为了把"看起来做完了"变成"能证明做完了"。

命令使用总前提（先读这个）：本手册所有命令的默认场景是——项目已经打开，Claude Code 会话已经在项目目录下启动。此后所有操作都在 Claude Code 输入框里完成，输入只有三种：
① 斜杠命令 /xxx（调会话内功能）；② bash 直通 !命令（你自己敲 shell，输出进对话，不经过 Claude 理解）；③ 自然语言 + @文件 引用。
全文只有三个场景需要回到系统终端：安装 / 升级 Claude Code 本身、启动一条新的并行会话（worktree）、CI 脚本调用。凡出现这三种情况，文中均已显式标注「系统终端」，其余命令一律在会话内敲。

第 0 步 · 路由：这个需求该走几步

先判断规模，再决定走几步。判据不是改动大小，是爆炸半径 + 你能不能快速验证。

需求规模走哪些步说明
单行修复 / 单文件小改直接做跳过 1–4直接说 + 附验证命令。改完跑测试，绿了就 commit。错了重来比修更快
单模块功能1 简化 + 5 + 6不需要正式 SPEC，但要有验收清单
跨模块 / 新功能全流程 1–8必须写 SPEC.md，必须过 plan mode，必须独立验证
从零起项目全流程 + 定原则先立项目原则，再进 specify

唯一判据：你能不能在 30 秒内判断结果对不对？能 → 直接做；不能 → 至少走第 2 步（定验收）。
反例：改一个被 20 处引用的公共函数——哪怕只动一个文件，也不能"直接做"。

第 1 步 · 拷问需求（不写一行代码）

目标

把模糊想法变成无歧义的表述。产出是文字，不是代码。

用什么 skill

Skill来源仓库作用
brainstorming obra/superpowers 苏格拉底式设计拷问：先探清意图、约束与替代方案，再收敛到架构决策

superpowers 是 GitHub 上 stars 最高的 Claude Code skills 集合（约 28 万），MIT 许可，一条命令装全套，约 1.2M 次安装量。

怎么装

# 方式一：插件市场（推荐）
/plugin marketplace add obra/superpowers-marketplace
/plugin install superpowers@superpowers-marketplace

# 方式二：skills.sh CLI（在系统终端敲，不是 Claude Code 会话里）
npx skills add https://github.com/obra/superpowers

# 只装单个 skill
npx skills add obra/superpowers --skill brainstorming

验证装好了没

/help          # 应该能看到 /superpowers:brainstorm 等命令

它生效的标志：新开一个会话，说"我要做个功能"，它会先反问你澄清问题，而不是直接开始写代码。
如果它还是直接写代码，说明 skill 没加载——按下面"附表 H"的排查清单走。

敲什么命令

# 会话已经开好了（启动目录就是项目根），先给会话命名，以后能按名字找回
/rename retrieval-cache

# 之后想回到这条会话，在新开的窗口里敲
/resume retrieval-cache

会话还没开怎么办：在 PyCharm / IDEA 终端里 cd 到项目根目录，敲 claude 回车进入——这是全文唯一一次需要自己敲 claude 启动的地方，之后所有操作都在输入框里完成。

对话里怎么说（可直接抄）

我要给检索接口加 Redis 缓存。先别写代码。
用 brainstorming 拷问我这个需求：
- 哪里说得不清楚？
- 有哪些隐含假设？
- 有哪些更简单的方案我没想到？
把问题一次问完，我统一回答。

顺手查细节（不污染上下文）

/btw 这个仓库的检索入口在哪个文件
/btw 现在用的 Redis 客户端是什么，key 前缀怎么定的

/btw 的答案永不进入对话历史——查细节走它，别问在主线里。

产出（三样，缺一不可）

  • 一句话需求：做成什么样，说给外人听他也懂
  • 风险清单：不确定的点、可能被忽略的边界
  • 被否掉的方案 + 理由：防止后面又绕回来
检查点：你能不能用一句话说清"做完是什么样"？说不清 → 别往下走。

第 2 步 · 定规格与验收清单

目标

把"要做的事"翻译成"怎么证明做完了"。核心主张：先有规格，后有代码，规格是活的文档。

用什么 skill

Skill来源仓库作用
writing-plans obra/superpowers 把需求拆成有序可测的任务，每步含：改什么文件、完整代码、怎么验证
writing-skills obra/superpowers 元 skill：教你按最佳实践写新 skill（要先装它，再扩展自己的）

如果你的 ~/.claude/CLAUDE.md 已经写了项目规范，它就是"项目原则"，不用另建 constitution。

对话里怎么说

用 writing-plans 帮我写一份 SPEC.md：
- 涉及的文件与接口签名
- 明确不在范围内的部分
- 端到端验证步骤（要能命令化）
写之前先用 AskUserQuestion 问清关键决策点，直到没有歧义。

SPEC 四要素（按重要性排序）

模块内容为什么
验收清单可勾选、可命令化没有验收项的 spec 就是散文
边界与非目标不改 schema、不引新依赖"不做什么"比"做什么"更防跑偏
接口契约函数签名、字段类型、错误码并行与集成的地基
现有约定给 2–3 个样板文件胜过写十条抽象规则

验收清单要写成这样（可执行）

## 验收清单
- [ ] `pytest -x tests/test_retrieval_cache.py` 退出码 0
- [ ] 相同 query 连打两次，第二次向量检索埋点计数为 0
- [ ] `python cache_hit_rate.py` 输出 >= 0.30
- [ ] 法条更新后 5 分钟内缓存失效（手改库验证）
- [ ] `redis-cli info memory` 占用 < 300MB

对比一下就知道差距：
✗ "缓存要生效" · "性能要提升" · "功能正常"
✓ "第二次调用不触发向量检索，埋点计数为 0" · "P95 < 200ms，用 mvn -q test -Dtest=OrderBenchTest 验证"

必须做的一步（拦掉一半跑偏）

复述一遍你理解的 SPEC，尤其是"不做什么"的部分。别开始写代码。
检查点：清单里每一条都能勾选吗？有没有"什么时候算做完"的明确定义？

第 3 步 · 派子代理探现状

目标

搞清楚代码现在长什么样，但别让它塞满你的上下文。子代理读一百个文件只还你一份结论。

用什么 Agent

Agent / 方式来源仓库适用场景
自然语言委派 内置 一次性调研，不想建文件
--agents '{...}' 内置 CLI 参数 想临时限定工具或模型
现成子代理集合 VoltAgent/awesome-claude-code-subagents 100+ 现成定义，挑一个抄进 .claude/agents/
dispatching-parallel-agents obra/superpowers 并发子代理工作流的标准配方

找现成 agent 的地方：VoltAgent/awesome-claude-code-subagents（100+，按职能分类）。
找现成 skill 的地方：hesreallyhim/awesome-claude-code（21K stars，按分类）· travisvn/awesome-claude-skills · anthropics/skills（官方）。

敲什么命令

# 方式一：自然语言委派（最常用）
让子代理读一下 retrieval 模块，说清：
1) 现在的召回链路（BM25 + 向量 + RRF 的调用顺序）
2) 现有的 Redis 用法（key 命名、TTL、序列化）
3) 和这次改动可能冲突的地方
只给结论，不要贴大段代码。

# 方式二：用 /agents 建一个可复用的只读调研 agent（会话内）
/agents
# → Create new agent → 名字填 scout → description 写触发时机
# → tools 只勾 Read / Grep / Glob → prompt 写：
#   你只做只读调研，绝不修改文件。输出：调用链、关键文件行号、风险点。
# 建好后长期复用：@scout 看一下 retrieval 的调用链

# 方式三：显式点名，保证跑一次
@"debugger (agent)" 看一下这次改动可能踩到哪些历史坑

@-mention 只保证"派给谁"——提示词内容仍由 Claude 撰写。想固定行为，就把规则写进 agent 的正文里。

检查点：它给的结论里有没有"我不确定"的地方？有 → 让它去补，别带进下一步。

第 4 步 · 出计划并亲手改

目标

在动手前把方案想清楚。Plan 的真正价值不是给 Claude 看，是给你自己看。 大约八成的情况，计划一出来你就发现需求本身有问题，而这一步成本几乎为零。

先搞清楚第 4 步和第 5 步的关系——这不是先后两步，是内外两层循环。
第 4 步是外循环：任务 1 → 任务 2 → 任务 3，管"按什么顺序干什么、每批干到哪停"。
第 5 步是内循环：执行每个任务时，任务内部走"写失败测试 → 看到红 → 最小实现 → 看到绿 → 重构"。
writing-plans 拆计划时，每个任务本来就配着验证命令——所以不是"第 4 步把代码写完、第 5 步再补测试"，而是"第 4 步派活，每个活的干法就是第 5 步"。

用什么 skill

Skill来源仓库作用
writing-plans obra/superpowers 把需求拆成有序可测任务，每步含文件路径 / 完整代码 / 验证方式
executing-plans obra/superpowers 按计划分批执行 + 每批 checkpoint，卡住就停不硬冲
subagent-driven-development obra/superpowers 计划拆给子代理执行，主代理只做验收

敲什么命令

命令 / 键位作用
/superpowers:writing-plans直接调起写计划 skill
/superpowers:executing-plans计划批准后分批执行
Shift+Tab循环权限模式，直到 ⏸ plan mode on
/plan 给检索加缓存，先看现有实现直接从命令行进计划模式，更快
Ctrl+G把计划丢进编辑器直接改（别在对话里反复纠）
Ctrl+T任务列表，跨上下文压缩存活
/context看上下文被谁吃掉了

对话里怎么说

1) 让子代理读一下 src/auth，说明 session 与登录是怎么处理的
2) 用 writing-plans 把"加 Google OAuth"拆成计划
   → 计划出来后按 Ctrl+G 在编辑器里改（别在对话里反复纠）
   → 按 Ctrl+T 让它拆成有验证命令的阶段
3) 计划我认了，用 executing-plans 执行，每批结束停下等我确认
   → 大批次想并行就切 subagent-driven-development
检查点：计划里每一条都能对应到一条可运行的验证命令吗？

第 5 步 · 测试先行，再让它实现

目标

给"做完了"一个客观判据，而不是听 Claude 说做完了。Anthropic 官方实测：开箱即用的 Claude 是个糟糕的 QA agent——它会识别出合理问题，然后说服自己"这没什么大不了"并批准。

本步是第 4 步的"内循环"，不是第 4 步干完之后的下一步。
executing-plans 按 PLAN 逐个任务执行时，每个任务内部都走本步的红绿循环：先写这个任务的失败测试 → 亲眼见红 → 最小实现 → 见绿 → 重构，然后才轮到下一个任务。
计划里每个任务自带的"验证命令"，就是在这里用的。

用什么 skill

Skill来源仓库作用
test-driven-development obra/superpowers 强制 RED → GREEN → REFACTOR。官方口径：先于测试写出来的代码会被删掉
systematic-debugging obra/superpowers 四阶段根因流程：复现 → 隔离 → 定位 → 验证
root-cause-tracing obra/superpowers 沿调用链向上追溯，找到真正的源头而不是表象

敲什么命令

# 先让它写会失败的测试
用 test-driven-development skill。先写会失败的测试：
- 相同 query 两次调用，第二次不触发向量检索
- 法条更新后缓存失效
写完跑一遍，把红色输出贴给我。

# 自己敲一遍，确认真的红（关键！）
## Java
!mvn -q test -Dtest=OrderIdempotentTest
## Python
!pytest -x tests/test_retrieval_cache.py

红了之后才让它动手：

测试红了。现在实现最小改动让它变绿，
只改 retrieval.py 和 cache.py，不要重构别的地方。

绿了就提交（会话内 bash 直通，! 开头）：

!git add -p                                 # 分块暂存，剔掉无关改动
!git commit -m "feat(retrieval): query 结果缓存"
闸门一 · 不红不许实现。 没看到真实的失败输出，就不许它开始写实现代码。

并行时（可选）

# 先让 Claude 建独立 worktree（会话内自然语言即可，别自己敲）

第 6 步 · 换个人来验证

目标

让没参与实现的执行者验收。这是"doer–verifier 分离"，也是官方三智能体架构（planner / generator / evaluator）的核心。

用什么

方式来源仓库说明
verification-before-completion obra/superpowers 最关键的一个：禁止在跑过验证命令、出示输出之前声称"完成了"
/verify 内置 对照正在运行的应用确认改动生效
@"verifier (agent)" VoltAgent/awesome-claude-code-subagents 现成的验证子代理定义，100+ 个可直接拷进 ~/.claude/agents/，全新上下文、不带作者的想当然
/loop 5m /verify 内置 定时巡检，适合"改完等它慢慢跑"
/goal 条件 内置 设完成条件，跨轮自动干到满足

敲什么命令

# 内置验证
/verify

# 派独立验证子代理（推荐）
# 定义从 GitHub 现成拷：VoltAgent/awesome-claude-code-subagents
@"verifier (agent)" 启动服务，发 10 个真实 query，
报告首 token 耗时、缓存命中率、内存占用，
再跑相邻的查询流程。不要改代码，只报告。

# 不想装子代理就用内置 Explore（只读、全新上下文）
让一个只读子代理检查 retrieval/ 的改动是否生效，
必须给出命令 + 输出 + 退出码，不要改代码。

# 定时巡检
/loop 5m /verify

# 自动续跑到满足条件
/goal pytest 退出码为 0 且输出可见，
且没有修改 retrieval/ 以外的文件，或 15 轮后停止并总结

/goal                                       # 看状态
/goal clear                                 # 立刻停

# 自己再敲一次，看真实退出码（Claude 说"通过"不算数）
!pytest -x
!mvn -q test
闸门二 · 要证据，不要保证。 必须是「命令 + 输出 + 退出码」，不接受"已通过""看起来没问题"。

卡住了怎么办

症状处置
测试红了修不好/diagnosing-bugs + @"debugger (agent)"，先复现取证再二分
环境起不来会话内先敲 /doctor；还不行 → 退出会话，在系统终端 claude --safe-mode 重启
不知道它在干什么Ctrl+O 展开详细输出（MCP 调用默认折叠成一行）

第 7 步 · 审查与交付

用什么

命令 / skill来源仓库作用
requesting-code-reviewobra/superpowers交付前的自检清单：该带什么信息、怎么暴露设计决策
receiving-code-reviewobra/superpowers收到反馈后怎么回应、怎么避免无意义往返
defense-in-depthobra/superpowers多层校验：不是只加一道防线，而是层层可验证
/diff内置交互式 diff，能看每轮对话产生的改动——审查 AI 的最佳入口
/code-review内置审 diff 的正确性与清理点
/security-review内置只看安全漏洞，涉及接口必跑
/simplify内置清掉过度防御与重复代码

敲什么命令

# 1) 自己完整读一遍 diff
/diff

# 2) 双轴审查
用 requesting-code-review 审查当前 diff：一轴看是否符合编码规范，
一轴看是否满足 SPEC。只报影响正确性的问题，不要改代码。

# 3) 安全审查（涉及鉴权 / SQL / 文件上传必跑）
/security-review

# 4) 清理过度防御
/simplify

# 5) 提交前最后确认（会话内 bash 直通）
!git status
!git diff --stat
!git log --oneline -5

只审承重代码（Thorsten Ball 原则）

档位范围审查深度
承重核心逻辑、DB 迁移、鉴权、并发、资金相关逐行读
半承重接口签名、错误处理、缓存策略扫逻辑，看边界
非承重样式、日志文案、变量命名、注释放过

判据就一句："这段错了会不会炸掉核心？" 会 → 逐行；不会 → 放过。
一字不落地读 AI 代码不可持续，完全不读是灾难。分档是唯一的平衡点。

三个 AI 代码特有的坑

  • 幻觉 API：调用了不存在的方法或参数。动态语言最省事的办法是实际执行一次
  • 静默失败：空 catch、无日志 fallback。Claude 特别爱写，因为它倾向让代码"看起来能跑"
  • 过度防御：满屏判空、永远走不到的分支。不是 bug，但污染后续改动，review 阶段清掉

交付：Git 操作（会话内 bash 直通，! 开头）

!git status                  # 零风险，随时敲，先看清楚再动手
!git diff                    # 看未暂存的改动
!git diff --stat             # 快速扫一眼有没有"顺手改"
!git add -p                  # 分块暂存
!git commit -m "feat: xxx"   # 一个子任务一个 commit

第 8 步 · 收尾与沉淀

为什么单独一步

每个 bug 都要变成一条永久规则。 不沉淀，同样的坑你会踩第二次。官方的做法：合并后更新 memory，把"让 agent 意外的地方"写进去。

用什么 skill

Skill来源仓库作用

敲什么命令

# 1) 让 Claude 写交接文档
把本次的关键决策和踩过的坑写成 HANDOFF-2026-10-24.md：
做了什么、在做什么、下一步要验证什么。别超过一段。

# 2) 把新规则固化（用 writing-skills 的标准格式）
用 writing-skills 的格式，把这次踩的坑写成一条新 skill，
放到 ~/.claude/skills/ 下。

# 3) 清空，为下一个任务腾出干净上下文
/clear

为什么是 /clear 而不是 /compact：官方发现模型有 context anxiety—— 它"以为"自己快到上下文上限就提前收尾。压缩保留了连续性，但没给它 clean slate，焦虑还在。
所以长任务用「短会话 + 结构化 handoff 文档」，不是「一个长会话反复压缩」。
（注：Opus 4.5 之后官方说这毛病基本消失，他们又改回自动压缩了——说明harness 策略会随模型过期，要定期体检。）

上下文腐烂的三个可观测信号

  1. 开始重复你早就说过的要求 — 它在反复重读，没真正记住
  2. 开始"顺手改"你没让它改的地方 — 失控前兆
  3. 开始为错误辩解而不是修 — 上下文里已堆了矛盾指令

命中任一条 → 立刻停，写 handoff，/clear 重开。

检查点：下次开会话，能不能靠这份 handoff 直接接上？

# ~/.claude/agents/scout.md
---
name: scout
description: 只读调研代码库，返回结构化结论不贴大段代码。
当需要了解某个模块现状、调用链、已有用法时使用。Use proactively.
tools: Read, Grep, Glob
model: sonnet
---

你只做只读调研，绝不修改任何文件。
输出固定三段：
1) 调用链（文件:行号）
2) 已有的相关用法（命名 / 配置 / 序列化方式）
3) 与本次改动可能冲突的地方
不确定的地方明确写"未确认"，不要猜。
# ~/.claude/agents/verifier.md
---
name: verifier
description: 实际启动应用验证改动是否真的生效。
实现完成后、准备交付前使用。Use proactively.
tools: Bash, Read
---

启动应用，验证本次改动的行为，以及相邻的两条流程。
报告：你跑了什么、看到了什么、哪些行为与计划不符。
不要修改任何代码，只报告。
# ~/.claude/agents/reviewer.md
---
name: reviewer
description: 在全新上下文审查当前 diff，只报影响正确性的问题。
实现完成后使用。Use proactively.
tools: Read, Grep, Glob, Bash
model: sonnet
---

重点检查：
- 与 SPEC / 接口契约不符
- 静默失败（空 catch、无日志 fallback）
- 幻觉 API（不存在的方法或参数）
- 边界输入与超时是否有明确行为

按严重程度排序，带文件行号和修改建议。不要改代码，只报告。
# ~/.claude/agents/debugger.md
---
name: debugger
description: 系统化排障——先复现取证，再二分定位根因，输出含报错
原文与证据的排障报告。当出现测试失败、运行时报错、性能回退时使用。
   Use proactively.
tools: Read, Grep, Glob, Bash, Edit
model: sonnet
---

你是一个排障专家。规则：
1. **先复现**——拿到可重现的最小步骤和完整报错原文，不要猜
2. **再二分**——用最小改动逐步缩小范围，每次只验证一个假设
3. **输出报告**——包含根因、证据、修复建议；未定位时明确说"未确认"
不要在没有证据的情况下下结论。

热重载：改完 .md 文件几秒内生效，不用重启。例外：会话启动时该目录还不存在、之后才创建首个文件的情况。
