Claude Code 实战手册

从「能用」到「用好」· 一套可验证的工程流程 + 一份从零可复现的配置

适合你：已经在用 Claude Code / Cursor 等 AI 编码工具，但产出总要靠运气的人

心智模型（全文围绕它）：不是「怎么让 AI 写出我要的代码」，是「怎么让 AI 的产出可以被验证」。每一步操作，都是在把「看起来做完了」变成「能证明做完了」。

本手册分两部分，解决两个不同的问题：

  • Part I · 日常怎么干——路由、八步主流程、报错处理、上下文卫生、红线、速查表。解决「每一次任务怎么把它做对」。
  • Part II · 机器怎么装——从零配置的 12 个阶段：模型接入、hooks 闸门、15 个 skill、2 个子代理、插件、模板。解决「让机器替你把规矩守住」。

两部分互相咬合：Part I 里的每个动作，在 Part II 都有对应的 skill、agent 或 hook 兜底；Part II 装的每一件装备，都在 Part I 的流程里有明确的使用时机。

1路由：30 秒判走几步

多数人翻车的根源：对所有需求用同一档力度——大需求轻率直做，小需求过度流程。判据不是改动大小，是爆炸半径 + 能不能在 30 秒内验证。

情况走法做什么
改完能 30 秒验证直接做不写 SPEC。改完跑测试，绿了就 commit——错了重来比修更快
单模块轻量档拷打 + TDD + 验收：/brainstorming → tdd → @verifier。不写正式 SPEC，但要有验收清单
跨模块 / 新功能全流程第 1–8 步一步不省

2主流程：八步，先看谁来做

全流程档的八步。每一步先解决「谁来干」——主 Agent 还是子 Agent，再看怎么干。

步做什么执行者为什么是它
1拷打需求主要跟你来回问，子代理接不到你的回答
2写 SPEC主要你确认，且它是后面六步的锚
3探现状子（Explore）只读、输出是结论，原文不必进主窗口
4拆 PLAN主拆法取决于你的偏好，要你审
5执行主（默认）/ 子（并行时）单线改动连着上下文；任务独立才拆出去
6验收子（verifier）+ Hook实现者不能给自己判分；闸门是机器
7Review主要判断哪段承重，子代理不知道你的项目
8打扫战场主git 决策 + 你来拍板

分派原则一句话：输入能一句话说清、输出是结论、不需要跟你来回 → 子 Agent；需要判断、需要你拍板、前后要连着改 → 主 Agent。

代价要认：子 Agent 有自己的上下文，不占主窗口，但它看不到你刚才说过的话，也读不到你脑子里的背景。派它时任务书必须自包含——说清范围、说清只读、说清要交回什么。

别让它空手回来：要证据就明说「贴命令 + 输出 + 退出码」，否则它只回一句「没问题」，你还得自己再跑一遍。

STEP 1 · 主 Agent

拷打需求：先当甲方，再当甲方

/brainstorming      ← 需求还模糊，先澄清要做什么、为什么做
/grilling           ← 方案已经想好了，捶它：漏洞、反例、更简单的替代

产出不是文档，是一句话目标 + 明确的「不做什么」。后者比前者防跑偏。

STEP 2 · 主 Agent

写 SPEC：验收清单是唯一的第一要素

/writing-plans      + 模板 config/templates/SPEC.md.template
序内容判据
1验收清单每条 = 一条命令 + 一个退出码/可见输出。不能命令化的验收项等于没写
2边界与非目标「不改 schema、不引新依赖」这类硬边界
3接口契约函数签名、字段类型、错误码
4现有约定给 2–3 个样板文件，胜过十条抽象规则
5背景与目标1–2 行，给人也给 agent 看

没有验收项的 SPEC 就是散文。

STEP 3 · 子 Agent（Explore）

探现状：别在主对话里翻十个文件

派 Explore 子代理：找出这条链路的现状——入口在哪、数据怎么流、
谁在调用这个函数（列全）、现有测试覆盖了什么。只读，只回结论。

子代理要交回的答案就是五件事：请求从哪进、数据怎么流、数据库在哪读写、模型和工具在哪调用、报错查哪里。

这一步的产物直接决定第 4 步怎么拆——没摸清现状就拆计划，等于画图纸不看地基。

STEP 4 · 主 Agent

拆 PLAN：八成问题在图纸阶段暴露，成本为零

/writing-plans      + 模板 config/templates/PLAN.md.template
  • 每一步标注验证方式（步骤 → verify: 检查项）
  • 标清楚哪几步走 tdd、哪几步直接写
  • 审计划：Ctrl+G 把计划丢进编辑器亲手改
STEP 5 · 主 Agent 默认

执行：两道闸门必须过

场景用什么
默认，自己按计划做/executing-plans（主）
任务彼此独立，想并行/subagent-driven-development 或 /dispatching-parallel-agents（子代理写，主只验收）
写功能 / 修 bug，测试先于实现tdd（自动触发，不用喊）

闸门一 · 不红不许实现：没亲眼看到真实的失败输出，不许开始写实现。

闸门二 · 要证据不要保证：只认「命令 + 输出 + 退出码」，不接受「已通过」「看起来没问题」。

拆出去的前提：文件集不重叠。两个子代理改同一个文件，冲突得你自己收场——真需要并行又绕不开，先开 worktree 物理隔离。

节奏：分批 checkpoint，每批做完停下验收，不要一口气跑到底。

同一处改两次仍失败 → 不许再改，回滚重新生成。第三次之后的尝试基本都是错的，继续只是在给错误加论证。

STEP 6 · 子 Agent + Hook

验收：写代码的不能给自己判卷

自动的那一半：Stop 闸门已经替你做了——工作区有改动时自动跑项目测试，失败就阻止收工并把最后 30 行错误回传。你什么都不用做。

手动的那一半：需要对照 SPEC 逐条判定时，派独立验收者。

@verifier 只读验证这批改动：
1) 跑 <验收命令>，贴 命令 + 输出 + 退出码
2) 对照 SPEC.md 验收标准逐条核对：通过 / 未通过 / 未覆盖
3) 只读，不许改任何文件
4) 结论明确列出：达标的、没达标的、根本没测到的

为什么验收必须是子 Agent：谁写的谁判分，永远判自己及格。这是全套流程里唯一一条不能省的分工。验收只返回是否有问题——PASS 一行结论，FAIL 必须带命令 + 输出 + 退出码。

闸门要能跑，项目得先有测试命令

项目布局闸门认不认怎么办
有 tests/ 且装了 pytest认，自动不用配
package.json 里有 test认，自动不用配
测试是手跑脚本、没装 pytest不认，静默放行见下

不认就等于没装。闸门找不到命令，按设计直接放行——你以为有保护，其实裸奔。

pip install pytest
mkdir tests            # 目录必须先存在
# 把现有 smoke 脚本里的 test_* 函数搬进 tests/
# 加一个 pytest.ini：testpaths = tests

只有非标准布局才手写 .claude/verify.json：

{ "command": ".venv/Scripts/python.exe scripts/check.py", "timeout": 180 }

别把 e2e 脚本填进去。那种要先把服务起起来的，每轮跑一次拖几十秒，你几天后必然把它关掉——闸门一关，等于回到没装的状态。

STEP 7 · 主 Agent

Review：只审承重代码

/diff               ← 一切审查的入口，先看它到底改了什么
/code-review        ← 正确性 + 坏味道（当前 diff 或 PR）
/simplify           ← 清理过度防御、重复、多余抽象
/security-review    ← 专项扫漏洞
类型读法
承重（核心逻辑、DB 迁移、鉴权、并发、资金）逐行读
半承重（接口签名、错误处理、缓存策略）扫逻辑，看边界
非承重（样式、日志文案、变量命名）放过

判据一句话：「这段错了会不会炸掉核心？」一字不落读不可持续，完全不读是灾难。

AI 代码三个特有坑特征与对策
幻觉 API调不存在的方法。动态语言最省事的验法是实际跑一次，文档类用 context7 查
静默失败空 catch、无日志 fallback。AI 特别爱写，因为它倾向让代码「看起来能跑」
过度防御满屏判空、永远走不到的分支。不是 bug，但污染后续改动
STEP 8 · 主 Agent

打扫战场：坑固化成资产

/finishing-a-development-branch     ← 合并 / 提 PR / 保留 / 丢弃，四选一

踩到的坑，用 /writing-skills 固化成 skill，下次自动避开。这一步不做，前面八步白走一遍——同样的坑会再踩。

3报错怎么处理

分岔点只有一个：定位到了没有。

状态动作谁来做
刚开始报错systematic-debugging 自动接手，或派 @debugger（独立上下文更省）子或主
坏了但找不到为啥坏读 systematic-debugging 里的 root-cause-tracing.md（只查不修）子（只读，只交结论）
定位了，一行能治（参数、条件、typo）最小修复 + 回归测试验证主
定位了，但要动结构 / 思路本身错了Esc Esc 回滚 → 更新 SPEC/PLAN（把根因和防再犯写进去）→ 重新生成主
上下文脏了写 HANDOFF → /clear → 从第 N 步继续主
同一个错试了三次还没好换会话。第三次之后的尝试基本都是错的主（换会话）

查根因派子代理，修 bug 自己来。查根因是「读一堆文件、只要一个结论」，正合子代理的活；修是「改一处、跑一次、再改」，需要连续上下文，拆出去反而来回三趟。

两条纪律：

  • 先查不修 —— 没定位到根因就动手，改的是症状，下次换个入口还会坏
  • 根因写回 SPEC/PLAN —— 防再犯的那句话，比修好的那行代码值钱

4上下文卫生：易腐资产怎么管

模型的工作记忆就是这段对话的全部。它不是硬盘，更像 RAM——会腐烂。腐烂有三个可观测信号：

为什么是 /clear 而不是 /compact

/compact 保留了连续性，但没给模型 clean slate——它会「以为」自己快到上限，提前收尾（context anxiety）。长任务 = 短会话 + 结构化 handoff，不是一个长会话反复压缩。

例外：同一件事还在推进、只是对话变长，/compact 更划算。判断标准是任务是否还连续，不是 token 还剩多少。

状态栏就是仪表盘

ctx N%：<50% 绿、50–79% 黄、≥80% 红。到黄就该想收尾，到红基本只能 /clear。

顺手要用的

操作干什么
/rename 会话名给会话命名，方便之后找回
/resume 会话名切回某个会话
/btw 问题顺手一问，不污染主上下文
Ctrl+G把计划/长文本丢进编辑器手改
Esc Esc回滚到上一轮

打断操作：发现不对——重复要求、顺手改没让改的地方、为错误辩解——立刻按 Esc 打断，不要让错误继续累积。

5红线

红线为什么
已 push 的 commit 一律 revert，不 reset别人的仓库里已经有那份历史了
git reset --hard 前先 git status会丢弃所有未提交改动且不可恢复
记不住但 commit 过的东西，git reflog 捞只要 commit 存在过就能翻回来
承重代码没逐行读过，不许 commit出问题时的第一责任人是你，不是 AI
不引新依赖，除非明确写进 SPEC依赖是长期的维护成本，不是一行 import

前三条已经被机器接管：只要装了 Part II 阶段 7 的 PreToolUse 闸门，git reset --hard、git clean -f、git push --force、git checkout -- .、git restore . 会在执行前被拦截并说明后果。人的纪律会犯困，机器的不会。

7从零配置清单：12 个阶段

从空白机器到当前配置的全部步骤。按顺序做，每步末尾都有验证命令。目标环境：Windows 11 + Git Bash，配置目录 ~/.claude。

最终形态：1 个模型端点 + 2 个插件 + 15 个本地 skill + 2 个 sub-agent + 5 类 hook + 1 个状态栏 + 1 个 MCP。

配套文件都在本仓库 config/ 目录：settings.json.template、hooks/gate.js、hooks/gate.test.js、statusline.js、agents/、templates/、commands/、CLAUDE.md。照着清单做的时候直接复制，不用手敲。

阶段 0

装 CLI

npm i -g @anthropic-ai/claude-code
claude --version          # 应输出当前版本号

装好后先跑一次 claude，让它生成 ~/.claude/settings.json 骨架，再往下改。

阶段 2

模型接入（settings.json 的 env）

"env": {
  "ANTHROPIC_BASE_URL": "<你的 Anthropic 兼容端点>",
  "ANTHROPIC_AUTH_TOKEN": "<你的 token>",
  "ANTHROPIC_MODEL": "<模型名>",
  "ANTHROPIC_DEFAULT_OPUS_MODEL": "<模型名>",
  "ANTHROPIC_DEFAULT_SONNET_MODEL": "<模型名>",
  "ANTHROPIC_DEFAULT_HAIKU_MODEL": "<模型名>",
  "ANTHROPIC_DEFAULT_FABLE_MODEL": "<模型名>",
  "CLAUDE_CODE_SUBAGENT_MODEL": "<模型名>",
  "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC": "1"
}

兼容端点可以接任何 Anthropic 协议的服务（阿里云百炼、DeepSeek、智谱等），填它给你的 base_url 和模型名即可。

三条经验：

  1. 明文 token 是隐患。能挪到系统环境变量就挪；挪不了，至少别让这个文件进任何仓库。
  2. 所有角色指向同一个模型 = 没有分层。规划、审查、子代理全在一个模型上，这是能力天花板。
  3. 兼容端点常有不支持的能力。部分端点不支持 text.format 结构化输出，带 json_schema 的请求会被 400 拒绝——报错时先怀疑端点差异。

验证：claude 能正常对话，/status 里显示的模型名正确。

阶段 3

settings.json 其余部分

{
  "statusLine": {
    "type": "command",
    "command": "node C:/Users/<你的用户名>/.claude/statusline.js"
  },
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "node", "args": ["C:\\Users\\<你的用户名>\\.claude\\hooks\\gate.js"], "timeout": 10 }] }
    ],
    "Stop": [
      { "matcher": "",
        "hooks": [{ "type": "command", "command": "node", "args": ["C:\\Users\\<你的用户名>\\.claude\\hooks\\gate.js"], "timeout": 200 }] }
    ]
  },
  "enabledPlugins": {
    "ponytail@ponytail": true,
    "code-review@claude-plugins-official": true
  },
  "modelSettings": {
    "<模型名>": { "effortLevel": "xhigh" }
  }
}

三个坑：① args 里的 Windows 路径要用双反斜杠，写成单反斜杠会被吞；② Stop 的 timeout 要足够长（200 秒），跑测试会用到；③ 改完必须重启 CLI 才生效。

验证：claude 启动后底部出现状态栏，形如 模型 │ 目录 │ (分支) │ ctx 3%。

阶段 4

全局 CLAUDE.md

~/.claude/CLAUDE.md 会被每次会话自动加载。必须写的三块：

块内容
语言始终简体中文；代码注释、commit、文档默认中文；专有名词保留英文但要中文解释
选择场景强制中文凡是让用户做选择，选项一律中文，禁止 Yes/No/Allow/Proceed
目标驱动命令式任务转成可验证目标；多步任务先给计划，每步标注验证方式

编码风格那块不要自己写——交给 ponytail 插件，否则两套规则打架。

宿主机上的 AGENTS.md 如果也存在，改成只指向上面的 CLAUDE.md，别复制一遍内容。两份同时注入就是双倍 token 加双倍冲突。

完整样例见仓库 config/CLAUDE.md。

关键决策：触发方式要分两档。

档做法适合谁
自动description 保留原文便宜、漏了要命、信号明确：tdd、systematic-debugging、receiving-code-review、verification-before-completion
手动description 改成「仅在用户明确要求时调用」正文大、误触发贵、需要你拍板：其余 11 个

改完本地常驻描述从 2607 字符降到 820。收益不是省 token（只占 1.7%），是减少「该调哪个」的歧义。

验证：ls ~/.claude/skills 应列出 15 个目录。

阶段 6

Sub-agents：只读，是独立验收的前提

~/.claude/agents/ 下每个 .md，frontmatter 必须有 name 和 description，否则不加载。

---
name: verifier
description: 独立验收者：只读不改，亲自运行验收命令，用命令+输出+退出码逐条判定达标/未达标/没测到，结论只能是 PASS/FAIL/BLOCKED。
tools: Read, Bash, Grep, Glob
model: inherit
---
Agent作用关键设定
debugger系统化排障：复现 → 定位 → 最小修复 → 验证无复现不修复
verifier独立验收只读；只有 Read/Bash/Grep/Glob，没有 Write/Edit

verifier 不给写权限，是它能做独立验收的前提——不是靠它自觉。

验证：ls ~/.claude/agents 有两个文件，开新会话时 /agents 里能看到。

阶段 7

Hooks 与状态栏

statusline.js

读 stdin 的 JSON，输出 模型 │ 目录 │ (分支) │ ctx N%。用到的字段：

model.display_name · workspace.current_dir · context_window.used_percentage

宽度不够时砍掉分支，别砍上下文百分比——那是唯一的仪表盘。

gate.js（一套脚本管两个事件）

事件行为
PreToolUse(Bash)拦 git reset --hard、git clean -f、git push --force、git checkout -- .、git restore .；exit 2 并说明后果
Stop工作区有改动时跑项目测试；通过则零输出，失败则 exit 2 + 回传最后 30 行

Stop 闸门的三条自我保护：

  • stop_hook_active 为真时放行，避免死循环
  • 同一份 diff 只验一次（按 git status + git diff HEAD 做指纹）
  • 找不到可靠测试命令时直接放行，不猜

测试命令识别顺序：

顺序找什么
1项目 .claude/verify.json
2根目录 package.json 的 scripts.test
3.venv/Scripts/python.exe + tests/ → pytest -q
4都没有 → 放行

验证：

node ~/.claude/hooks/gate.test.js     # 应输出「gate.js 自检全部通过」

阶段 11

每个新项目要做的四件事

做不做判断
让闸门能跑标准 pytest / npm 项目零配置；测试是自定义脚本才写 verify.json
建一个空 tests/ 目录比写十条规范都有效——模型只往已存在的目录放文件
建 CLAUDE.md从模板复制，写清启动命令、测试命令、测试放哪
git init + 首次 commit没有 commit 就没有回滚点

闸门这一条最容易漏，也最致命。漏了它不会报错，只会静默放行——你以为有保护，其实裸奔。

测试位置同理。项目里没有 tests/ 时，模型会跟着现有结构把测试塞进 scripts/，因为新建目录比复用现有目录「改动更大」。等它塞了十几个文件再搬家，就是大工程。

8.3 维护约定

  • 改 settings.json 前先备份到 ~/.claude/backups/，改完重启。
  • 改 skill 前先备份，因为插件升级会覆盖插件目录下的文件，本地目录不会。
  • 每加一个 hook，先写自检。闸门自己挂了比没有闸门更危险——它会静默放行，你还以为有保护。

结语：判断自己升级了没有

不需要考试，就看三个行为标志：

  1. 拿到需求，第一反应从「怎么说提示词」变成「先判走几步、先定怎么验收」；
  2. 听到 AI 说「完成了」，条件反射是「命令、输出、退出码呢」；
  3. 每踩一个坑，产出物里多一个 skill 或多一行 CLAUDE.md，而不是多一声抱怨。

三条都做到，你就已经从「用过」毕业了。
