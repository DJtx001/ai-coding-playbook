从「能用」到「用好」

AI Coding 进阶教程 · 把「一句话让它写代码」升级为「一套可验证的工程流程」

适合你：已经在用 AI 编码工具，但产出总要靠运气的人

你是否中招？以下任意一条命中，说明你还停在「用过」阶段：

  • 开一个新需求，第一句话永远是「帮我实现 XXX」
  • AI 说「已完成」你就信了，运行才发现根本跑不通
  • 对话越拉越长，AI 开始遗忘早先的约束、顺手改你没让它改的文件
  • 生成质量全靠运气：好起来惊为天人，差起来一无是处，且你不知道差别在哪
  • 复盘时说不清「这次它为什么会写错」

一句话心智模型（本教程全文围绕它）：新手想的是「怎么让 AI 写出我要的代码」，高手想的是「怎么让 AI 的产出可以被验证」。每一步操作，都是把「看起来做完了」变成「能证明做完了」。

1心智模型升级：从生成到验证

「用过但用得浅」的核心症状不是不会写提示词，而是整个工作流里没有验证环节。对比两种工作流：

✗ 生成式工作流（大多数人的现状）

  • 提需求 → AI 输出代码 → 看起来对就贴上
  • 报错 → 把错误整段丢回去 → AI 补丁叠补丁
  • 跑不起来 → 「再试一次」 → 上下文越陷越深
  • 质量标准：AI 自己的声称（「已完成」「没问题」）

✓ 验证式工作流（本教程教的）

  • 提需求前先拷问：边界、替代方案、不做什么
  • 动手前先定验收清单：每条 = 一条命令 + 一个退出码
  • 实现走 TDD：测试必须先红，亲眼见红才许写实现
  • 完成前换个人验证：子代理只读核对，出示命令+输出
  • 质量标准：证据，不接受任何口头保证

这个转变不需要你学新工具，只需要在每个环节插入一个「证明」动作。后面各章给出的全是可操作的插入点。

2会话卫生：上下文是易腐资产

模型的工作记忆就是这段对话的全部。它不是硬盘，更像 RAM——会腐烂。腐烂有三个可观测信号：

为什么是 /clear 而不是 /compact

压缩（compact）保留了连续性，但没有给模型一块干净的白板——模型「以为」自己快到上限就会提前收尾、降低质量（context anxiety）。长任务 = 短会话 + 结构化交接，而不是一个长会话反复压缩。

HANDOFF.md 交接模板

停会话之前把「它其实没记住、新会话需要知道的东西」写下来，越像工单越好：

# HANDOFF.md
## 当前任务
（一句话说在做什么）
## 已完成
- 步骤 1-3，产物：SPEC.md / 测试文件路径
## 卡在哪
- 第 4 步 X 原因，已排除 Y、Z 两种假设
## 下一步
- 从第 N 步继续，先读 SPEC.md 和 PLAN.md
## 已知坑（勿再踩）
- 例：api/client.ts 的 timeout 单位是秒不是毫秒

新会话第一句固定为：读 SPEC.md、PLAN.md 和 HANDOFF.md，从第 N 步继续。

日常会话微操

动作用途
/rename 会话名给会话命名，方便日后切回来
/resume 会话名切换到别的对话，开新支线
/btw顺手一问不污染主线上下文（问完即弃）
/clear清空重来——配合 HANDOFF 使用，是常规操作不是失败标志

进阶隔离 · git worktree：要同时开两条互不干扰的任务线（比如一边重构一边修 bug），用 worktree 给每个会话一个物理隔离的工作目录，并发的子代理文件集再怎么重叠也撞不了车。

3路由：拿到需求先判走几步

多数人翻车的另一根源：对所有需求用同一档力度——大需求轻率直做，小需求过度流程。判据不是改动大小，而是爆炸半径 + 你能不能在 30 秒内验证结果。

「直接做」的安全网：即便是最低档，也要遵守——改完立刻跑测试，绿了才 commit；测试不红反绿（本来就该过的用例挂了）说明改坏了，直接回滚重来。这一档快的前提是舍得扔。

4主干流程七步走

下面进入全流程档的七步。先看一图流，再逐步展开。每一步都有一个共同主题：在声称之前，先要证据。

STEP 1

拷打需求 · 不写一行代码

先当甲方，再当甲方

需求到手直接开写，是「浅用」的最典型形态——AI 会替你默默做一堆隐性假设，等代码出来你才发现双方理解根本不一致。正确动作是让 AI 先采访你：

  • skillbrainstorming：发散，探清意图、约束和替代方案
  • skillgrilling：收敛，像设计评审一样逐轮逼问，直到架构决策全部落定

拷问的产物是一份「想清楚了」的共识——它直接决定第 2 步 SPEC 里「非目标」章节能写得多具体。这一步省一分钟，第 5 步还一小时。

STEP 2

写 SPEC.md · 规格说明书

验收清单是 spec 的第一要素

判断一份 spec 是不是散文，只看一点：每条验收项能不能翻译成「一条命令 + 一个退出码/可见输出」。不能，就是没写完。按重要性排序的五节：

章节写法要点
① 验收清单可勾选、可命令化。! pytest tests/x.py → 退出码 0 才算过
② 边界与非目标「不做什么」比「做什么」更防跑偏（例：不改 schema、不引新依赖）
③ 接口契约函数签名、字段类型、错误码——并行与集成的地基
④ 现有约定给 2-3 个样板文件路径，胜过十条抽象规则
⑤ 背景与目标1-2 行，给人也给 agent 看

为什么样板文件胜过抽象规则？抽象规则（「遵循项目风格」）每次解读都可能不同；具体文件路径是零歧义的锚点，agent 会自己去读并模仿。这也是后文「上下文指针」思想的第一次应用。

STEP 3

派子 Agent 探现状 · 只读

读代码这件事，别用主会话

「这个改动会牵扯到哪些地方」需要读十几个文件——把这些全文读进主会话，上下文当场烂一半。派子代理去读，只回传结论：

调查 X 模块的现状：哪些文件引用了它、现有测试覆盖到哪、
改动会波及哪些接口。只读，不改任何文件，返回结论清单。

多个独立调查可以同时派（skilldispatching-parallel-agents）；注意：子代理们的工作文件集若有重叠，必须配 worktree 物理隔离，否则互相覆盖。

STEP 4

出计划 · plan mode

八成问题在图纸阶段暴露，成本为零

  • skillwriting-plans 把 SPEC 拆成 PLAN：每一步标明哪些走 TDD、哪些直接写
  • 进入 plan mode：Shift+Tab 循环权限模式直到 ⏸ plan mode on，或 /plan 任务 直达
  • 计划出来后 Ctrl+G 丢进编辑器亲手改——这是全流程性价比最高的一分钟
  • 执行用 skillexecuting-plans：分批 checkpoint，每批停下验收；Ctrl+T 看任务进度（跨上下文压缩存活）
  • 大批次想并行：换成 skillsubagent-driven-development——计划拆给子代理执行，主代理只做验收

执行期报错分流（决定继续还是推倒，判据是「修复会不会动结构」）：

情况动作
代码报错，原因不明skillsystematic-debugging 查 bug；找不到为啥坏用 root-cause-tracing（只查不修）
定位了，一行能治（参数/条件/typo）最小修复 + 回归测试验证
定位了，但要动结构 / 思路本身错了Esc+Esc 回滚 → 更新 SPEC/PLAN（把根因和防再犯写进去）→ 重新生成
上下文脏了/clear 重开，第一句「读 SPEC.md、PLAN.md、HANDOFF.md，从第 N 步继续」

STEP 5

TDD 实现 · 闸门一

先于测试写出来的代码，会被删掉

闸门一 · 不红不许实现：没有亲眼看到测试真实的失败输出（RED），不许开始写实现代码。skilltest-driven-development 强制 RED → GREEN → REFACTOR 循环。

TDD 在 AI 工作流里的价值比对人更大——它是唯一能在机器层面证明「需求已被满足」的短路验证：测试红了，证明缺的就是这个；测试绿了，证明做完了，不接受任何形式的口头声称。而且 AI 写测试极快，TDD 对人的最大成本（测试编写时间）在这里几乎不存在。

测试的质量上限是形式化验证 / 穷举式验证——对核心逻辑（状态机、协议解析、金额计算）值得用 property-based testing 之类的工具逼近这个上限。

STEP 6

验收 · 闸门二

换个人来证明：写代码的不能给自己判卷

闸门二 · 要证据不要保证：必须是「命令 + 输出 + 退出码」，不接受「已通过」「看起来没问题」。skillverification-before-completion 禁止在出示验证输出前声称完成。

关键是验证者与实现者分离——写代码的会话已经积累了一堆「我做完了」的惯性，让它自己验收等于让考生自己改卷。派只读验证代理：

@verifier 只读验证这批改动：
1) 跑 !pytest -x，贴 命令 + 输出 + 退出码
2) 对照 SPEC.md 验收标准逐条核对：通过 / 未通过 / 未覆盖
3) 只读，不许改任何文件
4) 结论明确列出：达标的、没达标的、根本没测到的

零配置替代品：/verify 对照正在运行的应用确认改动生效；/loop 5m /verify 定时巡检；/goal 条件 设完成条件自动续跑到满足（/goal clear 立刻停）。

注意第 4 条「根本没测到的」——验收三态里最危险的是未覆盖：它意味着 SPEC 写了但没人验，下次回来看见绿灯会误以为过了。

STEP 7

审查 + 收尾

只审承重代码，把坑固化成资产

审查命令链（顺序即优先级）：

/diff                  ← 先看它改了什么（一切审查的入口）
/code-review           ← 自审正确性 + 坏味道
/security-review       ← 专项扫漏洞
/simplify              ← 清理过度防御与重复
/requesting-code-review ← 按清单整理信息，交付/开 PR
/receiving-code-review  ← 有脑地回应审查意见

AI 代码的三个特有坑（review 时专扫这些）

坑特征与对策
幻觉 API调用不存在的方法或参数。动态语言最省事的验法是实际跑一次；静态语言靠类型检查。文档类 MCP（context7）治它
静默失败空 catch、无日志 fallback——AI 特别爱写，因为它倾向让代码「看起来能跑」。review 时见 catch 必查
过度防御满屏判空、永远走不到的分支。不是 bug，但污染后续改动，/simplify 清掉

审查精力的分配原则

  • 承重（核心逻辑、DB 迁移、鉴权、并发、资金）→ 逐行读
  • 半承重（接口签名、错误处理、缓存策略）→ 扫逻辑、看边界
  • 非承重（样式、日志文案、命名、注释）→ 放过

判据一句话：「这段错了会不会炸掉核心？」一字不落逐行读不可持续，完全不读是灾难。

打扫战场

skillfinishing-a-development-branch：合并 / 提 PR / 保留 / 丢弃四选一。然后——这轮踩到的坑，用 writing-skills 固化成 skill。这是「用得浅」和「持续变强」的分水岭：坑不沉淀，就会永远用同样的方式再踩一遍。

5解剖一份真实配置：~/.claude 里该有什么

前面四章是「流程」，这一章是「装备」。下面这份配置以一台实际在用的机器为参照系，并已经把教程全文引用的 skill 全部按出处补齐——照着搭一遍，流程里的每个步骤都有现成工具对应。

读这份目录的正确方式：不是照抄文件清单，而是看它回答的三个问题——① 我的原则放在哪（CLAUDE.md）？② 我的方法固化成什么（skills/）？③ 我不想重复交代的废话谁替我接管（plugins/）？三个问题都有答案的机器，才叫「装备齐全」。

5.2 CLAUDE.md：全局原则，只写不随项目变的东西

真实样例（这台机器的全局指令全文只有 22 行）：

# 全局自定义指令

## 语言
- 始终使用简体中文回答用户。
- 代码注释、commit 信息、文档说明默认使用中文。
- 专有名词和报错原文可保留英文，但解释必须用中文。

## 编码行为
- 编码行为规范由 ponytail 插件接管（懒惰阶梯：YAGNI → 复用 →
  标准库 → 原生 → 已有依赖 → 一行 → 最小实现），此处不再重复定义，
  避免冲突。

### 想清楚再写（Think Before Coding）
- 不要替用户做隐性假设；不确定就先提问，不要猜。
- 存在多种合理解读时，把几种解读都列出来，不要默默选一种。
- 有更简单的方案时要说出来，必要时反驳用户的思路。
- 自己困惑时停下来，指明哪里不清楚并请求澄清。

### 目标驱动执行（Goal-Driven Execution）
- 把命令式任务转成可验证的目标，先定"怎样算完成"，再循环直到验证通过。
  - "修这个 bug" → 先写复现 bug 的测试，再让测试通过。
  - "加个校验" → 先写非法输入的测试，再让测试通过。
- 多步任务先给出简短计划：每一步标注验证方式（步骤 → verify: 检查项）。

三个可提炼的写法要点：

  • 显式让位：「编码行为由 ponytail 接管，此处不重复定义」——全局指令最怕两处规则打架，写清归属比写全规则更重要。
  • 把流程原则写死：「目标驱动执行」那一节，本质是把第 4 章的两道闸门写进了开机配置——不依赖你每次记得去说。
  • 短：22 行。CLAUDE.md 每个会话都占上下文，越长稀释越狠——每一行都该值回它的 token。

5.3 skills/：从一行路由到整条流水线

形态真实例子要点
完整方法论 skillgrilling：把需求采访组织成「设计树 + 前沿轮次」——每轮把当前所有能问的问题一次性编号问完，附推荐答案，等回答再进下一轮frontmatter 的 description 写清触发条件（"uses any 'grill' trigger phrases"），模型才知道何时该调
带旁文件的 skilltdd：SKILL.md 主线 + tests.md、mocking.md 两个专题；systematic-debugging 里则挂着 root-cause-tracing.md 与 defense-in-depth.md主文件长会稀释注意力，把专题拆成旁文件、在主线里用指针引用——指针措辞决定 agent 会不会真的去读
编排型 skillsubagent-driven-development + dispatching-parallel-agents：把计划拆给子代理并行执行，主代理只验收skill 也可以是「编排子代理的配方」——这是第 3 步探现状之外的第二个子代理用例
元 skillwriting-skills：教怎么写 skill，references/ 里还有 testing-skills-with-subagents.md（用子代理测你的 skill）工具的工具：学完能自己造工具

这里藏着一个全文反复出现的概念：上下文指针——skill 的 description、CLAUDE.md 里指向其他文件的那一行，都是指针。指针的措辞（而非它指向的内容）决定 agent 会不会真的去读；「重要目标藏在措辞含糊的指针后面 = 一个方差 bug，先磨措辞，磨不好再内联」。这解释了 5.2 里为什么样板文件路径胜过抽象规则，也解释了为什么 skill 建了却不触发时，先改 description 而不是改正文。

5.4 自己动手：新增一个 skill / agent 的最小操作

两个文件、十行字，就是一份能跑的装备：

# ~/.claude/skills/my-skill/SKILL.md
---
name: my-skill
description: 一句话说清"什么时候该用"——这是触发器，不是简介
---
正文写方法本身：步骤、判据、格式示例。短就是好。
# ~/.claude/agents/my-agent.md
---
name: my-agent
description: 子代理的"岗位说明书"：它只做什么、不做什么
---
系统提示词正文：角色、约束、输出格式。

5.5 出处与安装：教程引用的 skill 从哪来

本教程点名的 skill 几乎都来自同一个仓库：obra/superpowers（GitHub 上 stars 最高的 Claude Code skills 集合之一，MIT 许可）。三种获取方式：

# 方式一：插件市场（推荐，装全套）
/plugin marketplace add obra/superpowers-marketplace
/plugin install superpowers@superpowers-marketplace

# 方式二：skills.sh CLI（系统终端，不是会话内）
npx skills add https://github.com/obra/superpowers

# 方式三：只要单个 skill
npx skills add obra/superpowers --skill brainstorming

装完新开会话验证：/help 能看到 /superpowers:* 命令，或让 agent 列出可用 skill。来源对照：

内容出处

一个易踩的误解：教程里多次出现的 root-cause-tracing、defense-in-depth、testing-skills-with-subagents 不是独立 skill，而是 systematic-debugging 和 writing-skills 目录里的旁文件——拷 skill 时要拷整个目录，只拷 SKILL.md 会把它们弄丢。另外既然本机已有同源的 tdd，就不要再装 test-driven-development：同一规则两份副本，改了一处忘了另一处，两处指令迟早打架。

自建 vs 拿来：通用方法用社区的（维护成本低、经过大量实战校验），你项目特有的坑和约定才值得写成自己的 skill——那部分是任何人拿不走的资产，也是第 7 步「坑固化成 skill」的落脚点。

6翻车急救与红线

症状急救
AI 开始重复你早说过的要求 / 顺手改没让它改的 / 为错误辩解会话卫生三信号，立刻：写 HANDOFF → /clear → 新会话读 SPEC/PLAN/HANDOFF 继续
测试一直是绿的，但你明明还没实现测试写废了（断言了不存在的东西恒真）。回到闸门一：验证测试本身能红
代码「看起来能跑」但线上静默出错AI 坑之二静默失败。全局搜 catch 与空 fallback，逐个补日志/上抛
调用了一个查无此人的 API幻觉 API。静态语言看类型检查，动态语言实际跑一次；接 context7 类文档 MCP 治本
改到一半思路错了，补丁越叠越厚Esc+Esc 回滚到检查点，更新 SPEC/PLAN 写明根因，重新生成——不要原地续命
skill/agent 建了却不触发多半是 frontmatter description 措辞太弱（上下文指针问题）或文件编码坏了，见 5.4

三条红线（不展开 git 细节，只立规矩）：① 已 push 的 commit 一律 revert 不 reset；② git reset --hard 前必须先 git status——它会丢弃所有未提交改动且不可恢复；③ 真丢了 commit，git reflog 能救命，只要 commit 存在过就能翻回来。

结语：判断自己升级了没有

不需要考试，就看三个行为标志：

  1. 拿到需求，第一反应从「怎么说提示词」变成「先判走几步、先定怎么验收」；
  2. 听到 AI 说「完成了」，条件反射是「命令、输出、退出码呢」；
  3. 每踩一个坑，产出物里多一个 skill 或多一行 CLAUDE.md，而不是多一声抱怨。

三条都做到，你就已经从「用过」毕业了。
